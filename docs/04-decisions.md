## Technical

- Регистрация / облачная синхронизация (`docs/02-mvp.md`, v1.4) — вынесена из MVP намеренно: сначала нужно решить, что конкретно должна делать регистрация (только синхронизация данных тренировок, или больше) и какой стек для бэкенда, прежде чем проектировать. Порядок относительно PWA (v1.1) обсуждался отдельно: бэкенд сознательно НЕ двигаем раньше PWA — PWA целиком укладывается в текущую local-first архитектуру и не требует решений по бэкенду, а сам бэкенд будет спроектирован уже после того, как PWA будет сделан.
- Push Notifications перенесены из v1.1 в v1.3 (Регистрация/Cloud Sync) — полноценные push-уведомления (сервер решает, когда напомнить пользователю, даже если приложение закрыто) требуют бэкенда/push-сервиса, локальные напоминания без сервера не рассматривались как альтернатива. Поэтому push логически зависят от того же нерешённого вопроса про бэкенд-стек, что и регистрация/cloud sync — вынесены в одну версию с ними, а не решаются раньше.
- AI Coach передвинут с v1.3 на v1.4, после Регистрации/Cloud Sync — по той же причине, что и push: AI-фича почти наверняка тоже требует бэкенда (прокси к AI-провайдеру, чтобы не светить API-ключ на клиенте, лимиты запросов по пользователю), так что нет смысла проектировать её раньше, чем решён вопрос бэкенд-стека.
- **Nuxt + Vant — решено.** Vant — мобильный-first UI-kit, есть официальный `@vant/nuxt` модуль (авто-импорт компонентов, без ручной настройки). Даёт из коробки тач-friendly компоненты, которые как раз нужны такому приложению (bottom sheet, action sheet, calendar, tabbar) — не пришлось верстать вручную. Плюс собственная система тем через CSS-переменные (`--van-*`) и локали (`Locale.use`), которые позже пригодились для кастомизации цвета и i18n без доп. усилий.
- Раздел «Замеры» (`docs/02-mvp.md`, v1.5) — идея и предварительная форма данных зафиксированы, реализация не начата. Открытые вопросы на момент реализации:
  - Точный порядок/приоритет v1.5 относительно v1.2–v1.4 не финализирован — версия проставлена условно, просто чтобы не путать с текущим MVP.
  - Хранилище фото-прогресса. Остальные домены (`workout`, `catalog`, `settings`) используют `useStorage`/`localStorage` напрямую — для текста и чисел этого достаточно, но `localStorage` обычно ограничен ~5–10MB суммарно на origin, и несколько фото в разумном качестве съедят этот лимит быстро. На этапе реализации нужно отдельно решить хранилище именно для `ProgressPhoto` (например, IndexedDB через `idb`/аналог, или File System Access API) — не расширять этим лимитом остальные Measurements, у которых числовых данных на порядки меньше.
  - Компонентам не следует напрямую читать/писать `useStorage`-refs для Measurements — по аналогии с тем, как уже устроены `workout.ts`/`catalog.ts` (компоненты вызывают именованные действия стора, стор — единственная точка мутации). Это то, что должно сделать безболезненным переход слоя хранения на backend/cloud sync (v1.4) позже: меняется реализация внутри стора, а не вызывающий код.
