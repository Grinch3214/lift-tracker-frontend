## Technical

- **Регистрация / облачная синхронизация (`docs/02-mvp.md`, v1.3) — решено и реализовано (2026-09-04—05).** Изначально вынесена из MVP намеренно: сначала нужно было решить, что конкретно должна делать регистрация, и какой стек для бэкенда, прежде чем проектировать. Порядок относительно PWA (v1.1) обсуждался отдельно тогда же: бэкенд сознательно не двигали раньше PWA — PWA целиком укладывается в текущую local-first архитектуру и не требовала решений по бэкенду. PWA (v1.1) по факту так и не реализован раньше — Cloud Sync обогнал его в очереди; актуальную реализацию см. `CLAUDE.md`.
- **Что из уже реализованного должно синхронизироваться через Cloud Sync (v1.3), а что остаётся чисто локальным даже после появления бэкенда — решено и реализовано именно в этом приоритете.** Офлайн-архитектура (`ssr: false`, `useStorage`) не выпиливается в любом случае — бэкенд добавляется поверх как фоновая синхронизация, а не как замена локального хранилища. Полный список текущих ключей `useStorage` (`app/stores/*.ts`):
  - **В облако, приоритет 1**: `workouts` (`lift-tracker-workouts`, `workout.ts`) — вся история тренировок, самое ценное, что есть в приложении. Единственное, что при потере реально ощущается как катастрофа.
  - **В облако, приоритет 2**: `customMuscleGroups`/`customExercises` (`catalog.ts`) — пользовательские упражнения/группы, результат реального труда по настройке каталога под себя.
  - **В облако, приоритет 3 (дешёво добавить заодно с п.2, но не критично само по себе)**: `groupOrder`/`exerciseOrder` (`catalog.ts`) — порядок drag-and-drop в пикере. Тоже «настроил под себя», но не потеря данных, если сбросится — просто раздражает.
  - **Остаётся локальным**: `primaryColor` (`settings.ts`) — чисто косметика, ноль ценности в синхронизации.
  - **Остаётся локальным**: `restTimerMode`/`restTimerDuration`/`restTimerSoundEnabled`/`restTimerSoundId` (`settings.ts`) — настройки таймера отдыха. `restTimerSoundId` — это просто id из захардкоженного в коде каталога звуков (`public/sounds/`), а не пользовательский контент, так что синхронизировать нечего кроме самого выбора; не стоит того ради того, что теряется.
  - **Остаётся локальным**: `lift-tracker-locale` — язык интерфейса, хранится в cookie, а не в `localStorage` (отдельный механизм, см. i18n-раздел `CLAUDE.md`).
  - **Будущее (`docs/02-mvp.md`, v1.5, Замеры, не реализовано)**: `Measurement`/`MeasurementType` — та же логика, что и `workouts` (прогресс тела, не настройка), в облако. `ProgressPhoto` — тоже данные пользователя (не косметика), но требует отдельного решения по хранилищу бинарного контента на бэкенде (не то же самое, что синхронизация JSON-настроек) — уже зафиксировано ниже в решении по «Замерам».
- **Гостевой лимит (10 тренировок) считается отдельным счётчиком `guestWorkoutCount`, не количеством записей `localStorage`.** (2026-09-02) Причина: `Workout` создаётся уже при открытии дня (`getOrCreateWorkoutByDate`), даже без единого подхода внутри — если считать по сырым записям, пустые открытые дни несправедливо съедали бы лимит. Счётчик растёт при засчитанной тренировке и **не уменьшается** при удалении (иначе лимит можно было бы обходить удалением/пересозданием). Открытый вопрос до реализации: что именно значит "засчитана" — сейчас в модели данных нет флага завершения тренировки, нужно явно решить (создание `Workout` vs первый `SetEntry`) прежде чем писать счётчик.
- **`localStorage` после регистрации не выпиливается, а меняет роль** — из единственного источника правды (гость) в локальный офлайн-кэш поверх backend как source of truth. (2026-09-02) Совпадает с уже принятым принципом "компонент не мутирует `useStorage` напрямую, только через действия стора" (см. пункт про «Замеры» ниже) — переход на sync добавляется внутри существующих экшенов стора, не переписыванием вызывающего кода. Мутации остаются мгновенными локально (UI не ждёт сеть), синк с бэком — фоновый `push`, `pull` нужен только для мультидевайс.
- **Перенос гостевых данных при регистрации переиспользует `POST /sync/push`, отдельного эндпоинта импорта нет — решено и реализовано.** Деталь и обоснование зафиксированы на стороне бэкенда, см. `lift-tracker-backend/DECISIONS.md` и `lift-tracker-backend/ARCHITECTURE.md` раздел 5.
- Push Notifications перенесены из v1.1 в v1.3 (Регистрация/Cloud Sync) — полноценные push-уведомления (сервер решает, когда напомнить пользователю, даже если приложение закрыто) требуют бэкенда/push-сервиса, локальные напоминания без сервера не рассматривались как альтернатива. Поэтому push логически зависят от того же нерешённого вопроса про бэкенд-стек, что и регистрация/cloud sync — вынесены в одну версию с ними, а не решаются раньше.
- AI Coach передвинут с v1.3 на v1.4, после Регистрации/Cloud Sync — по той же причине, что и push: AI-фича почти наверняка тоже требует бэкенда (прокси к AI-провайдеру, чтобы не светить API-ключ на клиенте, лимиты запросов по пользователю), так что нет смысла проектировать её раньше, чем решён вопрос бэкенд-стека.
- **Nuxt + Vant — решено.** Vant — мобильный-first UI-kit, есть официальный `@vant/nuxt` модуль (авто-импорт компонентов, без ручной настройки). Даёт из коробки тач-friendly компоненты, которые как раз нужны такому приложению (bottom sheet, action sheet, calendar, tabbar) — не пришлось верстать вручную. Плюс собственная система тем через CSS-переменные (`--van-*`) и локали (`Locale.use`), которые позже пригодились для кастомизации цвета и i18n без доп. усилий.
- Раздел «Замеры» (`docs/02-mvp.md`, v1.5) — идея и предварительная форма данных зафиксированы, реализация не начата. Открытые вопросы на момент реализации:
  - Точный порядок/приоритет v1.5 относительно v1.2–v1.4 не финализирован — версия проставлена условно, просто чтобы не путать с текущим MVP.
  - Хранилище фото-прогресса. Остальные домены (`workout`, `catalog`, `settings`) используют `useStorage`/`localStorage` напрямую — для текста и чисел этого достаточно, но `localStorage` обычно ограничен ~5–10MB суммарно на origin, и несколько фото в разумном качестве съедят этот лимит быстро. На этапе реализации нужно отдельно решить хранилище именно для `ProgressPhoto` (например, IndexedDB через `idb`/аналог, или File System Access API) — не расширять этим лимитом остальные Measurements, у которых числовых данных на порядки меньше.
  - Компонентам не следует напрямую читать/писать `useStorage`-refs для Measurements — по аналогии с тем, как уже устроены `workout.ts`/`catalog.ts` (компоненты вызывают именованные действия стора, стор — единственная точка мутации). Это то, что должно сделать безболезненным переход слоя хранения на backend/cloud sync (v1.3) позже: меняется реализация внутри стора, а не вызывающий код.
