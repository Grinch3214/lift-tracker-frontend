# MVP

## Пользователь может

- начать тренировку без регистрации (выбрать дату — она и есть тренировка, отдельного создания/завершения нет)
- добавить упражнения
- создавать свои группы и упражнения
- записать подходы
- посмотреть историю

---

## Пользователь НЕ может

- общаться
- покупать подписку
- использовать AI
- получать достижения
- использовать готовые программы тренировок
- пользоваться социальными функциями
- регистрироваться и сохранять прогресс в облаке

## v1.3 — Регистрация / Cloud Sync (реализовано, 2026-09-04 — 2026-09-05)

Регистрация не блокирует использование приложения с первого запуска — только отложенное предложение. Гостевой режим: до `GUEST_WORKOUT_LIMIT` (10) тренировок без регистрации, счётчик `guestWorkoutCount` (`app/stores/guest.ts`) монотонный — не уменьшается при удалении, тренировка засчитывается по первому `SetEntry`, не по созданию `Workout`-записи (иначе открытый-но-пустой день сжигал бы лимит). Любая успешная регистрация/логин навсегда закрывает гостевой режим на этом устройстве (`guestStore.exhaustLimit()`), независимо от реального счётчика — иначе логаут на устройстве без гостевой истории (чистый профиль, или сразу логин) открывал бы новый лимит.

Cloud Sync — push/pull для тренировок и кастомного каталога (группы/упражнения/порядок), Last-Write-Wins по `updatedAt`. Первый синк переиспользует обычный `POST /sync/push` (вызывается из `authApi.ts#authenticate()`, не блокирует UX логина при сбое) — отдельного эндпоинта под "перенос при регистрации" нет, см. `lift-tracker-backend/ARCHITECTURE.md` раздел 5. Дальше — фоновые триггеры (`app.vue`): смена видимости вкладки, восстановление сети, редкий таймер-подстраховка; намеренно не привязаны к отдельным мутациям стора, гранулярность синка — целая тренировка. `localStorage` не выпиливается как концепция — меняет роль на локальный офлайн-кэш поверх backend как source of truth, мутации по-прежнему пишутся туда мгновенно.

Технические детали (стор/файловая структура, все найденные по пути баги и фиксы) — `CLAUDE.md`; история реализации по датам — `CHANGELOG.md`.

## v1.5

Раздел «Замеры» — отслеживание изменений тела отдельно от тренировок (вес, обхваты и т.д.) плюс фото-прогресс.

- Новый пункт бокового меню «Замеры» → отдельная страница `/measurements`.
- Measurements — самостоятельный домен, не привязан к Workout/WorkoutExercise ни в данных, ни в UI.
- Пользователь выбирает тип измерения из списка. На старте — стандартные типы: Вес, Грудь, Талия, Бёдра, Бицепс, Бедро. «Вес» выбран по умолчанию. Архитектура с самого начала должна допускать пользовательские типы измерений — по тому же принципу, что уже есть у кастомных упражнений/групп мышц (см. `app/stores/catalog.ts` в `CLAUDE.md`): статичный набор встроенных типов + отдельно хранимые пользовательские, объединяемые через lookup-функции.
- Экран конкретного измерения (например, «Вес»): текущее/последнее значение, график изменения во времени, история всех записей, кнопка «Добавить замер».
- «Добавить замер» — модальное окно: значение (number), комментарий (необязательно), дата (по умолчанию сегодня). Пользователь может указать и прошедшую дату — важно для переноса старых измерений при первом знакомстве с приложением.
- Единица измерения не хранится в самой записи — она определяется типом измерения (`MeasurementType`), значение везде остаётся простым `number` (никаких отдельных типов данных под кг/см на этом этапе).
- Отдельный блок «Фото прогресса» внутри раздела «Замеры» — НЕ часть конкретного измерения (не привязан к «Вес», «Грудь» и т.д.), отдельная сущность со своей датой. Загрузка фото, дата съёмки, хронологический просмотр; в будущем — сравнение «до/после».

Предварительная форма данных (ориентир для реализации, не финальный API):

```
MeasurementType { id, name, unit, isCustom }
Measurement { id, measurementTypeId, value: number, comment?, date }
ProgressPhoto { id, date, ...фото }
```

MeasurementType → Measurement[] (один тип → много записей, например Weight → [18.08: 72.4, 10.08: 73.1, 01.08: 74.0]). ProgressPhoto — отдельно от всего этого, привязан только к дате.

Открытые архитектурные вопросы — см. `docs/04-decisions.md`.
