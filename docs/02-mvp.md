# MVP

## Пользователь может

- начать тренировку без регистрации (выбрать дату — она и есть тренировка, отдельного создания/завершения нет)
- добавить упражнения
- создавать свои группы и упражнения
- записать подходы
- посмотреть историю

---

## Пользователь НЕ может

- общаться
- покупать подписку
- использовать AI
- получать достижения
- использовать готовые программы тренировок
- пользоваться социальными функциями
- регистрироваться и сохранять прогресс в облаке

## v1.3

- **Регистрация** — не блокирует использование приложения с первого запуска, только отложенное предложение. Гостевой режим: до `guestWorkoutLimit` (10) тренировок без регистрации. Счётчик — отдельное монотонное состояние `guestWorkoutCount` (растёт при засчитанной тренировке, не уменьшается при удалении), **не** равен количеству записей в `localStorage` напрямую — открытый-но-пустой день не должен сжигать лимит. По достижении лимита: кнопка "Начать тренировку" блокируется, показывается предложение зарегистрироваться ("мы перенесём твой прогресс"); локальные данные при этом не удаляются и не блокируются на чтение.
  - Открытый вопрос (решить перед реализацией счётчика): точный критерий "тренировка засчитана" — создание `Workout`-записи (открыл день) или наличие хотя бы одного `SetEntry` в ней? Сейчас в модели данных нет явного флага "тренировка завершена" (`Workout` = просто день, см. `CLAUDE.md`), значит и "завершённость" для лимита нужно определить отдельно, не через несуществующее поле.
- **Cloud Sync** — первая синхронизация после регистрации переиспользует обычный `POST /sync/push`, вызванный один раз со всеми накопленными гостевыми тренировками — отдельного эндпоинта под "перенос при регистрации" нет и не планируется, см. `lift-tracker-backend/ARCHITECTURE.md` раздел 5 и `lift-tracker-backend/DECISIONS.md`. Признак успеха — `rejected: []` в ответе, не просто `HTTP 200`; только тогда можно чистить `localStorage`.
  - После успешного переноса `localStorage` не выпиливается как концепция — меняет роль: был единственным источником правды (гость), становится локальным офлайн-кэшем, source of truth — backend. Дальнейшие мутации по-прежнему пишутся в `localStorage` сразу (UI не ждёт сеть — офлайн-первый принцип сохраняется и после регистрации), затем синкаются в фоне через `push`; `pull` нужен только для мультидевайс-сценария (второй телефон/компьютер), не для сценария "только что зарегистрировался".
  - Порядок реализации: сначала один вертикальный срез целиком (гостевые тренировки → регистрация → `push` → после перезагрузки данные приходят с backend), `pull` и мультидевайс — отдельным шагом после того, как этот срез руками проверен.
  - **Обязательная доработка перед реализацией `push`:** у `Workout` (`types/workout.ts`) сейчас нет поля `updatedAt` (только `createdAt`) — без него LWW-сравнение на бэке физически не с чем делать (`lift-tracker-backend`, `PushWorkoutDto.updatedAt` уже обязательное поле контракта). Нужно добавить `updatedAt: string` в тип и обновлять его в сторе при каждой мутации тренировки (добавление/изменение/удаление подхода или упражнения) — по той же логике, что `createdAt` сейчас проставляется при создании.
- Push Notifications (перенесены из v1.1 — полноценные push требуют сервера, который решает когда напомнить, даже если приложение закрыто; локальные напоминания без бэкенда не рассматриваются)

## v1.5

Раздел «Замеры» — отслеживание изменений тела отдельно от тренировок (вес, обхваты и т.д.) плюс фото-прогресс.

- Новый пункт бокового меню «Замеры» → отдельная страница `/measurements`.
- Measurements — самостоятельный домен, не привязан к Workout/WorkoutExercise ни в данных, ни в UI.
- Пользователь выбирает тип измерения из списка. На старте — стандартные типы: Вес, Грудь, Талия, Бёдра, Бицепс, Бедро. «Вес» выбран по умолчанию. Архитектура с самого начала должна допускать пользовательские типы измерений — по тому же принципу, что уже есть у кастомных упражнений/групп мышц (см. `app/stores/catalog.ts` в `CLAUDE.md`): статичный набор встроенных типов + отдельно хранимые пользовательские, объединяемые через lookup-функции.
- Экран конкретного измерения (например, «Вес»): текущее/последнее значение, график изменения во времени, история всех записей, кнопка «Добавить замер».
- «Добавить замер» — модальное окно: значение (number), комментарий (необязательно), дата (по умолчанию сегодня). Пользователь может указать и прошедшую дату — важно для переноса старых измерений при первом знакомстве с приложением.
- Единица измерения не хранится в самой записи — она определяется типом измерения (`MeasurementType`), значение везде остаётся простым `number` (никаких отдельных типов данных под кг/см на этом этапе).
- Отдельный блок «Фото прогресса» внутри раздела «Замеры» — НЕ часть конкретного измерения (не привязан к «Вес», «Грудь» и т.д.), отдельная сущность со своей датой. Загрузка фото, дата съёмки, хронологический просмотр; в будущем — сравнение «до/после».

Предварительная форма данных (ориентир для реализации, не финальный API):

```
MeasurementType { id, name, unit, isCustom }
Measurement { id, measurementTypeId, value: number, comment?, date }
ProgressPhoto { id, date, ...фото }
```

MeasurementType → Measurement[] (один тип → много записей, например Weight → [18.08: 72.4, 10.08: 73.1, 01.08: 74.0]). ProgressPhoto — отдельно от всего этого, привязан только к дате.

Открытые архитектурные вопросы — см. `docs/04-decisions.md`.
