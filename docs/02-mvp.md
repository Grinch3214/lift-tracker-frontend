# MVP

## Пользователь может

- начать тренировку без регистрации (выбрать дату — она и есть тренировка, отдельного создания/завершения нет)
- добавить упражнения
- создавать свои группы и упражнения
- записать подходы
- посмотреть историю

---

## Пользователь НЕ может

- общаться
- покупать подписку
- использовать AI
- получать достижения
- использовать готовые программы тренировок
- пользоваться социальными функциями
- регистрироваться и сохранять прогресс в облаке

## v1.3

- **Регистрация** — не блокирует использование приложения с первого запуска, только отложенное предложение. Гостевой режим: до `GUEST_WORKOUT_LIMIT` (10) тренировок без регистрации. Счётчик — отдельное монотонное состояние `guestWorkoutCount` (`app/stores/guest.ts`, растёт при засчитанной тренировке, не уменьшается при удалении), **не** равен количеству записей в `localStorage` напрямую — открытый-но-пустой день не должен сжигать лимит.
  - **Решено (2026-09-04):** критерий "тренировка засчитана" — первый `SetEntry`, а не создание `Workout`-записи. Реализовано в `AddSetSheet.vue#confirm()` — считает сумму сетов по всем упражнениям дня *до* вызова `workoutStore.addSet()`, инкрементирует только если она была 0.
  - **Реализовано (2026-09-04):** UI-гейт по достижении лимита — `GuestLimitGate.vue` заменяет FAB добавления на плашку-баннер, тап открывает `GuestAuthModal` (email+пароль, переключатель регистрация/логин ссылкой снизу). Плюс постоянная точка входа в `TheSidebar.vue` (не дожидаясь лимита) — пункт "Войти", открывающий ту же модалку в режиме логина; после логина — строка с email + "Выйти" вместо пункта меню.
  - **Реализовано (2026-09-04):** проактивное напоминание до достижения лимита — иначе пользователь узнаёт о регистрации только на 10-й тренировке. `GuestRemainingNudge.vue`, всплывающий тост на отметках `GUEST_NUDGE_MILESTONES` ([8,6,4,2] оставшихся, `app/stores/guest.ts`), тригерится из `AddSetSheet.vue#confirm()` сразу после инкремента счётчика. Автоскрытие через 4.5с, тап — открывает `GuestAuthModal` в режиме регистрации. Не показывается уже залогиненным.
  - **Реализовано (2026-09-04):** настоящая регистрация/логин — `app/utils/api.ts` (`apiFetch`, обёртка над `$fetch` + `runtimeConfig.public.apiBaseUrl` из `.env`) и `app/utils/authApi.ts` (`registerUser`/`loginUser`/`logoutUser`/`restoreSession`) реально бьют в `POST /auth/register`/`/login`/`/logout`/`/refresh`. `app/stores/auth.ts` хранит `refreshToken` персистентно, `accessToken` — только в памяти (не в `localStorage`, живая сессия туда не пишется), `restoreSession()` обменивает `refreshToken` на новый `accessToken` при загрузке приложения (`app.vue#onMounted`). `AuthModal.vue` показывает ошибки (занят email/неверный пароль/лимит запросов/невалидные данные) и лоадер на кнопке. Проверено вживую через headless-браузер против поднятого докер-бэкенда — регистрация, логин с неверным паролем, логаут.
  - **Решено и реализовано (2026-09-04):** гостевой лимит после логаута — момент любой успешной регистрации/логина навсегда "закрывает" гостевой режим на этом устройстве (`guestStore.exhaustLimit()`, вызывается из `authApi.ts#authenticate()`), независимо от реального счётчика. Без этого логин на устройстве с 0 гостевых тренировок (чистый профиль, или сразу логин без гостевого использования) давал бы уже зарегистрированному юзеру полный новый лимит в 10 бесплатных тренировок после логаута.
- **Cloud Sync — реализовано (2026-09-04), пункты 1–4 из плана.** `app/stores/sync.ts` (`lastSyncedAt`) + `app/utils/syncApi.ts` (`runFullSync` = `pushLocalData` → `applyRejected` → `pullRemoteData`). Первая синхронизация после регистрации переиспользует обычный `POST /sync/push`, вызванный один раз внутри `authApi.ts#authenticate()` (после `exhaustLimit()`), не блокируя UX логина при сбое — отдельного эндпоинта под "перенос при регистрации" нет, см. `lift-tracker-backend/ARCHITECTURE.md` раздел 5. `apiFetch(..., {auth: true})` теперь умеет `Authorization`-заголовок и авто-`refresh` по 401 (один повтор), нужно только для `/sync/*`. Проверено вживую (headless-браузер + прямые запросы к бэку): гостевая тренировка → регистрация → данные реально долетают до БД → логин с того же аккаунта на чистом профиле → тренировка приходит через `pull`. То же самое отдельно проверено для кастомного каталога (группа/упражнение/порядок), включая восстановление `isCustom: true` на пуле.
  - `localStorage` не выпиливается как концепция — меняет роль: был единственным источником правды (гость), становится локальным офлайн-кэшем поверх backend. Мутации по-прежнему пишутся в `localStorage` сразу (UI не ждёт сеть), синк — отдельным шагом.
  - **Реализовано (2026-09-05):** пункт 5 — фоновые триггеры синка (`app.vue`). Намеренно НЕ привязаны к мутациям стора (`addSet` и т.д. остаются чистыми, ничего не знают про сеть) — гранулярность синка целая `Workout` (решение бэка), триггер на каждый подход заново слал бы всю растущую тренировку. Вместо этого: `visibilitychange` — основной и самый частый триггер (при уходе из вкладки/сворачивании и при возврате), сработает `{immediate: true}` и на маунте, если юзер уже залогинен; `useOnline()` — синк при восстановлении связи; редкий таймер-подстраховка (7 минут, `SYNC_BACKSTOP_INTERVAL_MS`) — только пока вкладка видима, для сценария "не сворачивает приложение" (например, юзер смотрит на отсчёт `WorkoutRestTimer`, а не переключается на другое приложение между подходами — тогда `visibilitychange` не сработает вообще). Все триггеры активны только при `authStore.isAuthenticated`. `runFullSync()` дешёво дёргать "на всякий случай" — `pushLocalData()` не бьёт в сеть, если нечего слать (см. фильтрацию по `updatedAt`/`lastSyncedAt` ниже).
  - **Побочный фикс (2026-09-05):** `api.ts#refreshAccessToken()` стал single-flight (конкурентные вызовы шарят один промис) — с несколькими независимыми триггерами синка риск двух одновременных вызовов `POST /auth/refresh` с одним и тем же (уже ротированным после первого использования) `refreshToken` перестал быть гипотетическим.

## v1.5

Раздел «Замеры» — отслеживание изменений тела отдельно от тренировок (вес, обхваты и т.д.) плюс фото-прогресс.

- Новый пункт бокового меню «Замеры» → отдельная страница `/measurements`.
- Measurements — самостоятельный домен, не привязан к Workout/WorkoutExercise ни в данных, ни в UI.
- Пользователь выбирает тип измерения из списка. На старте — стандартные типы: Вес, Грудь, Талия, Бёдра, Бицепс, Бедро. «Вес» выбран по умолчанию. Архитектура с самого начала должна допускать пользовательские типы измерений — по тому же принципу, что уже есть у кастомных упражнений/групп мышц (см. `app/stores/catalog.ts` в `CLAUDE.md`): статичный набор встроенных типов + отдельно хранимые пользовательские, объединяемые через lookup-функции.
- Экран конкретного измерения (например, «Вес»): текущее/последнее значение, график изменения во времени, история всех записей, кнопка «Добавить замер».
- «Добавить замер» — модальное окно: значение (number), комментарий (необязательно), дата (по умолчанию сегодня). Пользователь может указать и прошедшую дату — важно для переноса старых измерений при первом знакомстве с приложением.
- Единица измерения не хранится в самой записи — она определяется типом измерения (`MeasurementType`), значение везде остаётся простым `number` (никаких отдельных типов данных под кг/см на этом этапе).
- Отдельный блок «Фото прогресса» внутри раздела «Замеры» — НЕ часть конкретного измерения (не привязан к «Вес», «Грудь» и т.д.), отдельная сущность со своей датой. Загрузка фото, дата съёмки, хронологический просмотр; в будущем — сравнение «до/после».

Предварительная форма данных (ориентир для реализации, не финальный API):

```
MeasurementType { id, name, unit, isCustom }
Measurement { id, measurementTypeId, value: number, comment?, date }
ProgressPhoto { id, date, ...фото }
```

MeasurementType → Measurement[] (один тип → много записей, например Weight → [18.08: 72.4, 10.08: 73.1, 01.08: 74.0]). ProgressPhoto — отдельно от всего этого, привязан только к дате.
